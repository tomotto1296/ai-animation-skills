# アニメーションの品質確認（QC＋自己レビュー）

実績: 129作品・166試行。やり直しの約半分は「ちらつき」「静止」「黒/単色」の自動チェックで、残りの多くは**自動チェックを通ったあとの見た目の問題**だった。一覧と原因は、`docs/failure-catalog.md`。

## 初回の確認（自動）
このスキルを初めて使うときは、最初に `python scripts/doctor.py` を実行して、環境が足りているかを確かめる（足りないものと、直し方が表示される。`--fix` を付けると、直せるもの（npm install など）はその場で直す）。ユーザーに手で準備させる前に、まずこれを試す。

## 0. 作り始める前（手戻りを減らす順序）
1. **意図した静止・フラッシュ・暗転・単色は、最初の書き出しの前に宣言**（`qc.json` の `expect`）。書き出して落ちてから宣言して通すのは禁止（やるなら post-hoc と記録に明記）。宣言した区間以外は厳しく見る
2. **0秒のコマから主役を見せる**: 透明・真っ暗・背景だけで始めない（黒/単色で落ちる）。フェードインは「最初のコマから薄くても見える」程度に
3. **明るさが一気に変わる演出は 0.4〜0.5 秒の smoothstep**: 暗幕・モーダルの背景・白フラッシュ・街灯の点灯・ページめくり・面の入れ替わり。明るい面が暗い面を1コマで覆わない。境目には 260px ほどのグラデーション
4. **ちらつきは「明るさの差 × 覆う面積の速さ」で決まる**: 全画面ワイプで明暗差175なら、1コマで覆う割合を 5.7% 以下に。`easeInOutCubic` は最大の傾きが平均の3倍で ΔYAVG が20になった → `easeInOutSine`（最大1.57倍）＋ワイプ1.5秒＋差し色を明るさの近い色にして最大 8.97（#016）。インクの滲みは覆う面積が時間にほぼ比例して増えるよう半径を設計する
5. **ease は区間ごとに。それでも残る明滅は「面の食い込み」を疑う**: 全体に1回だけ ease をかけると途中が最速になるので区間ごとに分けるが、#040 は分けたあとも星形の2コマで −6.2・−7.8 が残った。**主因は、厚みのある板（solidify）どうしが食い込み、見える面が白↔赤に急に切り替わっていたこと**。閉じている間だけ外向きに 0.09mm 離すと最大 1.6 に下がった。折りや開きで白と赤の面が入れ替わる速さは 0.42/0.32 秒→0.65/0.6 秒で収まった（最大 11.64→8.32）
6. **終わり際まで動かす**（最後の区間は「表示を全部止めたら何が動くか」で確かめる。経過時間の数字だけが動いていて、実は静止していることがある #089）: 尺を延ばすなら終わりの区間にも動きを。波・煙・光は上限で切られて静止になりやすい（光の波が明るさの上限に当たって見えない、など）
7. **白い題材は地を暗く**: 白判定は「画素の下位10%の輝度が 220 以上（TV レンジ）」。最も明るい地でも RGB 237 未満に（#006 は板 #fbfcfd→#e9edf0、#eceff2→#d6dbe0 と周辺減光で PASS。「明るく」ではなく「暗く」して直した）
8. **黒判定は「暗い画素の割合」**（既定 pix_th=0.1）: 背景の中央だけ明るくしても、98.6% の画素が暗いままなら黒。**中間の色まで持ち上げる**（暗い紺 #060913 は #1a2442 へ）。暗い地の作品は最初の書き出しの前に `profiles: ["dark"]`（地の輝度が8%程度でも既定の黒判定に当たる）。確かめ方: 0コマ目の PNG を1秒の MP4 にして blackdetect をかける
9. 暗い作品は profile `dark`（黒判定を緩める）。静止が主役の作品は `static`

**意図した明滅は、まず設計で避ける。宣言するのは、避けられない演出だけ**（検証 T1 の判断）: 例えば蛍光灯のまたたきは「管そのものは鋭く光らせ、部屋全体の明るさは 0.25 秒ほどの箱形でならす」設計にすると、`expect` を書かずに最大差 8.7 で QC を通る。宣言が必要なのは、白フラッシュ自体が演出の本体のとき（画面全体が一瞬で変わる）。宣言は書き出しの前に。
- **白フラッシュが演出の本体のとき（検証 T2）**: 設計でならすと「パッ」ではなく点灯に見える（立ち上がり 2 コマで YAVG 30→81→135、1コマ <10 に収めるには 7 コマ=0.23秒以上）。この場合は **`expect` に宣言する**。手順: ①draft で連続コマを測る（`scripts/ydelta.py`）②立ち上がりを短く、**減衰だけを設計**する（tau 0.16秒 → 1コマ -18、0.24秒 → 最大 -11.3。長い尾 0.9 秒）→ 検出が「立ち上がり 2 コマ（＋減衰 1 コマ）」に絞れる ③宣言区間は検出に合わせて狭く取る（開始 -0.05〜開始 +0.2 秒）④書き出しの前に確定する。**宣言どおりの場合、QC の結果は WARN（「除外した検出 N 件」の注記）が正常**。FAIL・未宣言の検出がなければ良い。壁などの最大を RGB 236 に clamp して白判定を避ける。強い明滅（1秒に3往復超）にならないよう回数・間隔も確認（二連フラッシュでも、≥22 の変化が上昇側だけなら往復にならない）。光過敏への配慮として、1秒に3回を超えるフラッシュは避ける
- **白い題材（雪・霧・白い紙）の設計（検証 T4 吹雪の灯台）**: 白判定は「画素の**下位10%**の輝度が 220 以上」なので、**明るい粒が多くても、背景が暗ければ当たらない**。地を暗く（空 RGB(8,12,28)→(70,62,92)、海 (10,16,30)、周辺減光 alpha 0.45）、雪の基本色は中間（(110,124,156)）にして、光線・灯の光の中だけ明るく。雪の最大色を RGB(236,240,250) に clamp。霞は色を中間の灰青に。結果は YLOW 最大 62（しきい値 220 に対し余裕 158）、YAVG 54.6〜89.6 で `expect`・`dark` 指定は不要。**YLOW の測り方**: `ffmpeg -i v.mp4 -vf signalstats,metadata=print -f null -` で `lavfi.signalstats.YLOW` を見る（見本: `scripts/ydelta.py` の YAVG を YLOW に変える）
- **QC を通るだけでは「吹雪に見える」とは限らない**: 細い点だけの雪は QC を通ったが吹雪に見えなかった（2600粒）。目安: 画面に約 5000 粒、横流れの線の長さ = 風速/30 × 0.55、霞を強めに。見た目の合否は QC では分からない
- **加算の半透明を層にして縁をなめらかにする**: 光線を台形3層にすると縁が段に見えた → 7層にしてなめらかに（検証 T4）
- **文字レイアウトの検査（検証 T6 エンドロール）**: `mock_canvas_check` の `measureText` は仮値（1文字10px）なので、**幅の検査は本番のブラウザの `setup` で `measureText` して、`console.log('[metric] ' + JSON.stringify(...))` で `render_meta.json` に残す**。測るもの: 最大の行幅（上限を決める）、左右の余白の最小（目標 150px 以上）、縮小率（長い名前は 58→50px、56字の英語名は 58→54px など）、折り返しの数、隣り合う行の箱のすき間の最小（負なら重なり）。**止まる位置で、直前の行が画面内に残らないか**も見る（END の上に直前の名前が残った → END までの距離を伸ばした。draft で発見）。止めた絵は静止判定になりやすいので、宣言せず弱い動き（2%の拡大の息づかい、線の伸び、フェードイン、背景の星の明滅）を残して freeze 0 にした（最大フレーム差 0.18 でも通った）。黒い背景は真っ黒にせず放射グラデ (26,28,44)→(9,10,16) にして、`dark` profile を併用（YAVG 35〜39）
- **静止の見逃しに注意（検証 T8 で判明し、この `qc.py` は修正済み）**: 旧版は freezedetect の区間全体で「最大画素差が 12 超なら一部が動いている」として捨てていたため、止まり始めの落ち着く動きが1コマ入っただけで、**本物の 2 秒の静止を見逃した**（freezedetect 単体は検出していた）。いまの `qc.py` は、区間の中で最大画素差 12 以下のコマが `freeze_d` 秒以上続く区間だけを静止として返す（合成テストで、静止は検出し、一部だけが動く画面は誤検出しないことを確認）。**最後に止まる作品は、目視と PNG の連続コマ差でも確かめる**
- Windows の Python で `render_meta.json`・`qc.json` を読むときも `encoding='utf-8'` が要る（既定は cp932。T2・T6 で再発）
- 照らされる面の陰影は、「全体に暗幕を重ねる」より「面ごとに奥行きで陰影を付ける」ほうが、手前ほど強い減衰が自然に出る（T2 の廊下）
- Windows の Python は `open()`・`json.dump` の既定が cp932。`qc.json`（設定）を書くときは `encoding='utf-8'`、読むときも `encoding='utf-8'` を付ける
- 暗転して終わる作品（検証 T3）: 窓と月を常に見せて暗画素が98%に達しないようにし、流れる雲と煙で静止判定を避け、炎は 0.4 秒の smoothstep で消すと、`expect` なしで QC PASS（最終コマ付近の YAVG 最小 30.2、炎の消え際の最大差 4.9）。`dark` profile は指定する。**最終コマの暗さは、この1例では 30 前後でも黒判定が出なかった**（ほかの作品では保証されない。書き出し前に draft の QC で確かめる）

## 1. 自動チェック
```bash
python scripts/qc.py out.mp4 --config qc.json --size 1920x1080 --fps 30 --duration 12
python scripts/contact.py out.mp4 review/ --n 16 --cols 4 --full 0.5,3,9.5 --diff 1,5
```
- 結果 PASS / WARN / FAIL（FAIL で終了コード1）。`qc.json` に検出の区間・除外した理由が残る
- しきい値: ちらつき＝1コマで平均輝度 ≥10、強い明滅＝≥22 が1秒に3往復超、静止＝0.5秒以上（かつ最大画素差 ≤12）、黒/白/単色
- **誤検出もある**: 画面の一部だけが動く作品は「静止」と誤検出されうる（最大画素差が大きければ誤検出）。**逆に見逃しもある**: エンコードの雑音で静止が静止と判定されない（freezedetect が反応しない）。数字を鵜呑みにせずコンタクトシートで確かめる
- WARN で「宣言した演出が検出されなかった」は、宣言が合っていない合図。宣言を直す（作品を直すのではなく、書いた範囲が違う）
- **事前測定が QC の宣言より確実**: 明るさが急変しうる区間（場面転換・暗幕・雷）は、最初の書き出しの前にその区間の連続コマだけ draft で描き、PNG の平均輝度（×219/255+16）の1コマの差を測る。実例: #115 18.9→4.2（フェード0.35〜0.5秒＋壁の明かりの追従）、#122 10.09→3.2、#128 10.75→8.4、#088 は基準のならしだけでは −16 が残り、**表示する画像そのものも時間方向にならす**（目標へ毎フレーム20%）と最大4に
- **宣言すれば安全とは限らない**: 短い静止（1〜1.6秒）を expect に書いても、H.264 で静止中も差が YMAX 0〜1 残り、freezedetect が反応せず「宣言した演出が検出されなかった」WARN になる（#118）。短い静止は宣言せず、ごく弱い動きを残す方が確実（2秒以上の完全な静止なら検出されるはず。推測）
- 地の明るさ＋波を clamp の上に足すと波が見えない（#113: 地 0.78＋波 0.22 = 1.0）→ 地を 0.88 に下げ、波は「白寄りの色へ mix」。最後の止め絵は 0.5 秒以上止めない
- 幕・暗幕の不透明度は、モーダルなどの表示条件の**外**で別の時刻関数にして描く（条件が消えたコマで幕も一気に消える #122）
- 原因が分からない見え方は、**光が通るマスクなどの中間画像を1コマだけ画面に出して見る**（#065）
- ラベル・引き出し線の重なりは、コンタクトシートでは小さすぎる。1080p の1コマで確かめる（毎回 1〜3 か所見つかった）
- 直したら**別の試行として**書き出し直し、前の結果は上書きしない

## 2. 自己レビュー（QC が見つけない問題）
`reference/selfreview_checklist.md` の表を、コンタクトシート16コマと、気になる区間の等倍コマで確認する。主なもの:
- 文字: 右端・下端で切れていないか（**文字の幅を測ってから置く**）、背景の模様や別の表示と重なって別の字に見えないか、最後のカードが読める長さか（#012 は約0.8秒で消えて読めなかった）
- 体・向き: 腕や顔が別の部位に隠れていないか、角度の巻き戻り（-2π から線形に混ぜると体が回転して逆さまになる。最短経路で補間）、足の滑り、膝・足のめり込み
- カメラ: 傾き続けていないか、速さが遠景ばかりで止まって見えないか、主役が隠れる区間がないか
- 3D: 同じ奥行きの面が重なってかすれる（Z ファイティング）、ライト・映り込み、破片のブーリアンの失敗
- シミュレーション: 硬すぎて動きが見えない／柔らかすぎて輪郭が折れる／ゼリー同士の重なり
- 最後のコマが意図どおりか（余韻・結論のコマで終わるか）

**数値で確かめられることは全コマで数値化する**（見本: `scripts/check_pose_example.mjs`。T5 では書き出し前に、屈んだ間の自由足が氷の下 -32.6cm へ出ている・腕が 4.3cm 届かない、を見つけて直し、1回目の書き出しで QC PASS・自己レビュー問題なしになった）。**回転量は累積角（巻き戻しなし）で持ち、描画のときだけ三角関数に渡す**と、巻き戻りは構造上起きない（θ の単調増加を数値で確認）。「足の滑り」の定義は競技や動作ごとに決める（スケートは接地足が氷の上を進むのが正しい: スピン中は軸の真下に固定→水平移動 0、ジャンプ中は浮き量を見る）。高速回転（1コマ 60 度超）のワゴンホイール（逆回転に見える）の閾値は未確認（63.5度/コマで目視は問題なし）。人物が小さいと見栄えの判断が難しいので、主役の画面占有率（身長が画面高さの何%か）を決めておく。**（骨の長さの誤差、最大めり込み、面積比、折れ点数、NaN、輝度の最大変化）。目視は数コマしか見ない

## 3. 判定と記録
- PASS でも自己レビューで不合格なら**作り直す**（記録に「QC PASS だが自己レビューで不合格: …」と書く）
- 弱点は隠さず書く（自己評価の弱点: 光沢がやや控えめ、など）
- 時刻は実測（マーカー・ログ）を写す。**推定で書かない**。失敗した試行にも記録を付ける（0コマで失敗しても）
- 試行の上限を決めておく（この検証では 3回、条件付きで 5回）。上限に達したら失敗・条件付きとして正直に書いて次へ
